### Fixed
- **Any `smoke`/`flow` job (including a `chaos_inject`/`chaos_webhook` control test) silently destroyed the live database** — found live while running the new `chaos_webhook` kind against a real deployment for over an hour: `mission-control.db` got truncated to zero tables mid-process, twice, with no container restart, once crashing the durable-jobs worker thread outright (`sqlite3.OperationalError: no such table: jobs`). Root cause: `playwright/playwright.config.ts`'s HTML reporter had `outputFolder: path.join(repoRoot, 'reports')` — the exact same directory `reports/mission-control.db`, job/run history, and artifacts live in. Playwright's HTML reporter unconditionally *clears its entire outputFolder* before writing a report, even when zero tests run (reproduced directly: a throwaway project with `outputFolder` pointed at a directory containing an unrelated file wiped that file even though the run itself failed with "No tests found"). Every `smoke`/`flow`-shaped test invocation this server ever runs goes through this same config, so pointing the reporter at the bare `reports/` root meant the live database was destroyed on a predictable, recurring basis with zero warning. Fixed by scoping the HTML reporter to `reports/playwright-report/` instead — Playwright's own conventional folder name — leaving `mission-control.db` and everything else in `reports/` alone. New `tests/unit/test_playwright_reports_isolation.py` statically guards the config so this can't regress silently; confirmed it fails against the pre-fix config and passes against the fix. Live-verified end to end: ran a real `chaos_webhook` job (full Playwright smoke suite, 11 tests) against the fixed deployment and confirmed the database, its schema, and prior job rows all survived intact.
- **`db_assert` always rejected a correctly-shaped `db_secret`** — found live while wiring `zyvorai/argus-enterprise`'s new Watchfloor "DB assertion" panel up to a real `argus serve` instance: every request with a genuine `{"$secret": "env:NAME"}` reference 400'd with "db_secret is required and must be a `{'$secret': 'env:NAME'}` reference", even though the request sent exactly that shape. Root cause: `orchestrator/dashboard/durable_jobs.py::_validation_view()` (which sanitizes secret refs before `_validate()` re-checks params, so validation never sees a real secret value) collapsed any `{"$secret": ...}` value to a bare placeholder *string* — `db_assert`'s own `is_secret_ref()` re-check on `db_secret` then always failed against that string. Fixed by keeping the placeholder in the same `{"$secret": "env:NAME"}` shape (`env:VALIDATION_PLACEHOLDER`) instead of collapsing it, so any kind that re-checks a ref's shape during validation (not just its resolved value) still passes. New regression test `test_enqueue_db_assert_survives_validation_view` (exercises the real `jobs._validate()`, not a mock, unlike the existing `_validation_view` tests); updated the two existing tests that asserted the old bare-string placeholder. Live-verified end to end against a real `argus serve` + `argus-enterprise` pair: the same `db_assert` request now passes validation and fails only on the correct, later boundary (`environment secret 'DB_DSN' is not configured`).

Both fixed and locked in by a regression test that sends a real `SIGTERM` mid-run. `chaos_webhook` was live-verified end to end with **zero mocking of the actual mechanics** — a real mock experiment webhook (confirmed real `/start`/`/stop` POSTs received), a real target server, and a real Playwright browser running the control test, both outcomes, both directly and through the real dashboard UI. New `agents/chaos/` (`verdict.py`, `probe.py`, `inject_script.py`), new Security-panel cards. Tests: `test_chaos_verdict.py`, `test_chaos_probe.py`, `test_chaos_inject_script.py`, `test_chaos_jobs.py`; extended `test_sandbox.py`, `test_jobs_validate.py`. New `tests/unit/test_paths.py`.

The ROADMAP had lumped these in with `jobs.py`'s/`cli.py`'s thin subprocess/Playwright wrappers as "low marginal value," but they turned out to be small, pure `PipelineState -> PipelineState` transforms with real branching logic behind only one or two easily-mockable agent calls each — cheap and worth doing, unlike the genuinely thin wrappers they were grouped with. 65 new tests; whole-suite coverage 47% -> 50%. Every LangGraph pipeline node gets a `pipeline.<name>` span via a single wrapper in `orchestrator/graph.py`'s `build_graph()` (no changes to the ~19 individual node modules); every claimed job gets a `job.execute` span in `durable_jobs.py`'s worker loop with `job.status`/`job.duration_s` attributes. Live-verified (not just unit-tested): a real document-source pipeline slice produced real per-node spans, and a real job run through `DurableJobService` end to end produced a real `job.execute` span with correct attributes. Cross-replica trace propagation (enqueue → claim on different replicas) is named as open follow-on work in `ROADMAP.md`, not silently skipped. New `tests/unit/test_tracing.py`.

ON CONFLICT DO NOTHING` + `SELECT ... FOR UPDATE` for the same race-free semantics as its SQLite counterpart. Live-verified against a real local Postgres 14 instance across every method category plus two concurrency scenarios (10 workers claiming 10 jobs with zero drops/duplicates; 20 threads racing a brand-new requirement upsert with zero errors). New `tests/unit/test_postgres_store.py` (skips cleanly without a configured Postgres) wired into a new `postgres-quality` CI job against a real `postgres:16` service container, so it stays exercised going forward rather than bit-rotting. See `ROADMAP.md`.

### Fixed
- `MissionControlStore.upsert_requirement()` (added in the previous pass) had a real, unhandled `sqlite3.IntegrityError` race: unlike `claim_job()` elsewhere in this same file, its read-then-conditionally-write wasn't wrapped in `BEGIN IMMEDIATE`, so two overlapping pipeline runs (a schedule and a webhook-triggered run, say) upserting the same brand-new requirement id could both read "doesn't exist yet" and both attempt the insert. Reproduced live before fixing: 2 of 20 concurrent calls against the same id crashed with `UNIQUE constraint failed: requirements.id`; 0 of 20 after wrapping the method in `BEGIN IMMEDIATE`/`COMMIT`, matching the existing `claim_job()` pattern. New regression test in `tests/unit/test_requirement_store.py`.

### Added
- `GET /api/v2/requirements`, `GET /api/v2/requirements/{id}`, and `GET /api/v2/requirements/{id}/history` — the previous pass built durable, versioned requirement storage plus quality scoring but left it with zero HTTP exposure; anyone wanting to see a requirement's current score, content, or version history had to query SQLite directly. Read-only by design (requirements are written by the pipeline's own `fetch → parse → evaluate_quality` chain, never through this API), gated by a new `requirements:read` scope granted to both `viewer` and `operator` roles (`orchestrator/security/rbac.py`). New `tests/unit/test_requirements_route.py`. Live-verified against a real running `argus serve` instance (not just `TestClient`): seeded a real requirement via `MissionControlStore.upsert_requirement()`, hit all three routes over real HTTP, and confirmed a 404 for an unknown id.
- Durable, versioned requirement storage and a real second requirements source (documents), replacing the previous flat-JSON, GitHub-only, single-run-then-discarded pipeline:
  - `orchestrator/persistence/store.py` (schema v3): `requirements`/`requirement_versions`/`requirement_test_links` tables. `MissionControlStore.upsert_requirement()` only creates a new version when a requirement's content actually changed (content-hash comparison) — re-running the pipeline against an unchanged requirement is a no-op, not noise. `get_requirement`, `list_requirements`, `requirement_history`, `link_requirement_test`, `linked_tests`.
